## 3. MCC truth table (generated artefact)

Generated by ``tools/unit/get_status_truth_table.py`` from BR-02 (docs/01
section 6).  2⁷ = 128 rows; the complete table and the MC/DC pair table are
evidence artefacts.

* `evidence/raw/get-status-truth-table.csv` – full 128-row MCC table
* `evidence/raw/get-status-truth-table.md` – same table as Markdown
* `evidence/raw/get-status-mcdc-pairs.csv` – 7 MC/DC pairs (n+1 = 8 rows)

The MC/DC minimal set (7 pairs, n+1 = 8 rows, chain independence):

| Condition | True row (outcome) | False row (outcome) |
|-----------|-------------------|---------------------|
| **a4** stored status in (new, paused, down) | R0011111 → *new* | R0010111 → *up* |
| **a5** grace_start is None | R0010111 → *up* | R0010011 → *down* |
| **a6** now >= grace_end | R0010011 → *down* | R0010001 → *grace* |
| **a7** now >= grace_start | R0010001 → *grace* | R0010000 → *up* |
| **a1** last_start is set | R1010000 → *started* | R0010000 → *up* |
| **a3** with_started is true | R1010000 → *started* | R1000000 → *up* |
| **a2** now >= last_start + grace | R1100000 → *down* | R1000000 → *up* |

Each pair: Hamming distance 1 in the 7-bit condition vector, outcome flips
from one row to the next, every condition appears in exactly one pair
(condition independence).  Validated by the generator script (exit 1 on any
contradiction).

Per-row metadata in the CSV:

| Column | Meaning |
|--------|---------|
| `row_id`      | ``R`` + 7‑bit binary, e.g. ``R0011111`` |
| `a1` … `a7`   | Atomic Boolean conditions (evaluation order) |
| `evaluated`   | Conditions actually evaluated on this row’s path |
| `masked`      | Conditions *don’t care* on this row’s path |
| `outcome`     | ``up`` / ``started`` / ``down`` / ``grace`` / ``new`` |
| `feasible`    | ``yes`` / ``no`` (with reason if ``no``) |
| `mcdc_condition` | Which MC/DC pair this row participates in, or empty |

## 3.3 Realisation witnesses (how each atomic condition is made true / false)

| Condition | Witness construction (simplified) |
|-----------|-----------------------------------|
| **A1** (`last_start` set) | `last_start = NOW` (bit = 1) or `last_start = None` (bit = 0) |
| **A2** (`now >= last_start + grace`) | `last_start = NOW - 2*grace` → A2 true; `last_start = NOW - grace/2` → A2 false |
| **A3** (`with_started` kwarg) | Pass `with_started=True` or `False` in the test call |
| **A4** (stored status in new/paused/down) | `status="new"` / `status="paused"` / `status="down"` |
| **A5** (`grace_start is None`) | `kind="oncalendar"` with a schedule that has *no* next occurrence after `last_ping` (e.g. `"2020-01-01 00:00:00"` + `last_ping` in 2026) → `StopIteration` → `NEVER` → `grace_start=None`. Or `kind="simple"` with a `last_ping` that has already elapsed past the next expected run. |
| **A6** (`now >= grace_end`) | `last_ping = NOW - 2*grace - timeout` → grace_start = NOW - 2*grace → A6 true. Or `last_ping = NOW - grace/2 - timeout` → A6 false. |
| **A7** (`now >= grace_start`) | If A5 is false: `last_ping = NOW - grace/2 - timeout` → A7 true. Or `last_ping = NOW + grace - timeout` → A7 false. |

These witnesses are realised in ``tests/team/unit/test_get_status_mcc.py`` via
``_realization()`` and in ``test_get_status_edges.py`` via explicit fixture
construction.  The truth-table generator’s feasibility checker confirms every
row labelled ``yes`` truly has a model satisfying its evaluated conditions.

## 4. MC/DC pair realisation

The 7 MC/DC pairs are each realized by exactly one test case parametrized by
the truth-table row id.  The ``pytest -m mcdc`` flag runs only those 8 rows
(7 pairs).  The pairs validate Hamming‑1 bit differences, direction of change,
and outcome flip — the three pillars of MC/DC for a single‑decision path.

## 6. BR‑02 ↔ A1–A7 mapping (documented per the master prompt)

| BR‑02 decision condition (docs/01) | Atomic condition (this module) | Reference row |
|-----------------------------------|--------------------------------|----------------|
| C1: ``last_start`` set **AND** ``now >= last_start + grace`` | A1 ∧ A2 | R1100000 (down) / R1000000 (up) |
| C2: ``last_start`` set **AND** ``now < last_start + grace`` **AND** ``with_started=True`` | A1 ∧ ¬A2 ∧ A3 | R1010000 (started) / R0010000 (up) |
| C3: stored ``status ∈ {new, paused, down}`` | A4 | R0011111 (new) / R0010111 (up) |
| C4: ``grace_start is None`` (next elapse never) | A5 | R0010111 (up, never elapses) |
| C5: ``now >= grace_end`` | A6 | R0010011 (down) / R0010001 (grace) |
| C6: ``now >= grace_start`` | A7 | R0010001 (grace) / R0010000 (up) |
| C7: ``otherwise`` | ¬A4 ∧ ¬A5 ∧ ¬A6 ∧ ¬A7 | R0000000 (up) / R0000001 (grace) |

Each row in `evidence/raw/get-status-truth-table.csv` records its `evaluated`
and `masked` conditions; the mapping above shows how the documented BR‑02
decision table slots into the 7‑condition MCC structure.

## 7. BR‑03 transition map (pause / resume)

Per docs/01 section 6, the observed state transitions are:

| From → To | Condition | API result | Dashboard result |
|-----------|-----------|------------|------------------|
| `new` → `paused` | POST pause, rw key | 200, status=``paused``, flip recorded | 302 redirect to details |
| `paused` → `new` | POST resume, check was paused | 200, status=``new``, flip recorded | 302 redirect to details |
| `paused` → `paused` | Idempotent repeat pause | 200, no second flip | 302, no second flip |
| `up` → `down` | Fail ping (BR‑02 C1) | 200 (model), status flips | — |
| `down` → `up` | Success ping on down check | Allowed transition | — |
| `resume from non-paused` | API/ dashboard resume attempt | 409 (API) / 400 (dashboard) [candidate defect A‑03] | 400 |

The A‑03 discrepancy (409 vs 400) is filed as a defect in Phase 11, not
silently normalised in the tests.
